  - **2026-09-01 — The Mission Loop tables are empty in production.** `missions`, `mission_events`, and `evidence_snapshots` all had 0 rows in project `pkydkbuodikttfeawqsw` when the Strategic Delta was built, while the Foundry-layer tables (`actions` 8, `events` 11, `evidence_items` 4, `routed_requests` 4) had real data.   - **2026-09-01 — Anonymous auth means demo state is per-browser.** `signInAnonymously()` scopes missions by `user_id` under RLS, so a fresh device or cleared browser is a *new* user with zero missions. A demo on an unfamiliar device starts empty by construction, not by failure.
  - **2026-09-01 — Local dev cannot sign in without `.env.local`.** `src/lib/supabase/client.ts` falls back to the literal string `your-anon-key-here`, which constructs a client successfully but 401s on every call. Console 401s plus "Sign-in failed" locally are expected, not a regression.
  - **2026-09-01 — supabase-js never throws; check `error` on every write.** `insert()`/`upsert()` resolve with `{ error }` on RLS or constraint failures, so `try/catch` around an awaited write silently swallows failed persistence. Two Delta write paths and one mission write had exactly this bug (UI flashed "saved" on rejected writes). Pattern: always `const { error } = await …insert(…); if (error) throw error`.
  - **2026-09-01 — Strategic Delta corrections use `mission_events` as a transitional persistence path, not as canonical ownership.** For the current vertical slice, `mission_events` is the smallest existing user-scoped append-only persistence path for corrections: `routed_requests` and `events` remain the canonical owners of routing/correction chains and generic audit history, but both are `workspace_id`-keyed Foundry tables (routing schema fields: `execution_lane`, `selected_agent`, `repository`) that the anonymous-auth front door cannot write without new plumbing. That is an ownership/schema **gap**, not a redefinition of `mission_events`. This choice does not make `mission_events` the canonical generic recommendation/correction authority; a future human-level correction authority will require explicit schema reconciliation.
  - **2026-09-01 — The Delta is the front door; chrome above it competes with the demonstration.** On a 375px screen, Operational badges, filter pills, and a Mission heading delayed the product moment. The shipping-first state is insufficient context — design that path as the instrument, not as an empty dashboard waiting for fixtures. Cognition belongs in a localized field whose colour encodes state; a card-wide spectrum gradient reads as generic AI chrome.
  - **2026-09-01 — Insufficient-context fields below the Delta are not usable, even when they are real inputs.** On 1280×720 the finish-line control sat past the fold (`elementFromPoint` was `null`); labels were placeholders only; `Input` inline `--line-strong` borders read as static copy; `:focus-visible` hid mouse focus; `role="tabpanel" tabIndex={0}` and `aria-live` on the whole `.sd` steal inner-input focus on Safari/iOS. Put labeled `<input>`s *inside* the hero, live-region only on the move copy, tabpanel `tabIndex={-1}`, and a `:focus` ring that beats inline styles. Verify by clicking and typing on `localhost`, not only component tests.
  - Home is the Mission tab (`CodexApp` default `activeTab`). The next-action surface is the **Right Now** card, not Overview's Foundry readout and not a second panel. Visual emphasis belongs there. `.card` padding in `globals.css` is `!important`, so extra space has to come from an inner wrapper, not `Card` `style.padding`.

  - **2026-09-22 — A supplied step is an operation, and the explanation lists the clauses the engine targets.** "Record this step" writes `delta_step_supplied` with `{ step, targetId }`. Reload rebuilds the same operation id and runs it through `isConcreteMove` and inhibition. A step that passes becomes the move with provenance `supplied` (cyan status, not teal, not model). A step that only restates the destination stays on record and is inhibited as `not_a_move`. The Why panel lists every `proofSteps` clause, including short ones the splitter produced ("reload", "that same action").   - **2026-09-23 — Acceptance is rehydrated from the ledger, per mission, and accept is idempotent.** `loadAll` reads `delta_accepted` with the other Delta events and folds them oldest-first (`liveAcceptances`): the latest acceptance per mission is live unless a later `delta_corrected` or `delta_step_supplied` for that mission replaced it. The UI shows "Accepted" only when that move equals the Delta on screen, so a re-prediction clears it without a write. New rows store `{ move, candidateId }`; older rows are plain move text and still read. `mission_events` has no unique constraint, so `handleAcceptDelta` guards (mission, move) client-side. A model-derived move that comes back with different words after reload is honestly not "accepted" any more.
